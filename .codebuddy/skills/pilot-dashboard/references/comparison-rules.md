# Comparison rules

## Map options to metrics before comparing

Write this table before looking at any area. It prevents the most common error: justifying an option with a metric it does not move.

| Option | Metric it moves | Where it does little |
|---|---|---|

An option whose main effect is on speed cannot be recommended because a return rate is high. An option whose main effect is on a return rate cannot be recommended because a queue is long. If the pack states a limit on an option's effect, that limit is binding.

## Read the definition before the number

Any metric measuring one step of a longer process must not be used to make claims about the whole process. Check whether the column measures the on-screen step, or the elapsed time the resident experiences. These differ by weeks, and conclusions drawn from the wrong one are backwards.

Columns that are routinely misread:

- **Spend to date.** Past operating cost. It is not the price of the proposed pilot and not a measure of efficiency.
- **Application counts.** Volume, not pressure. Divide by staff to see pressure.
- **Satisfaction.** Comes from the residents who responded. It says nothing about those who gave up before responding.
- **Any average across areas.** Says nothing about the worst area, which is usually the one the decision is about.

## Derive load before comparing staffing

Where more staff is an option, compute applications per officer for every area and put it in the table. An area with a moderate application count and very few officers can be the most stretched, and a raw count will hide it.

## Check the period

For each metric, look at every month available, not the latest. Distinguish:

- **A sustained level.** Stable across the period. Structural, and a pilot can address it.
- **A trend.** Moving in one direction. State the direction and rate.
- **A spike.** One or two months. Do not build a quarter's pilot on it without saying that is what you are doing.

## Test the priority switch honestly

Recalculate from the table under the second priority. Rank the areas again on the metric that priority cares about, re-apply the option-to-metric mapping, and see which pairing wins.

Then state one of two things:

- The choice holds, and here is the figure that makes it hold under both.
- The choice changes, to this option in this area, for this reason.

A recommendation that changes with the priority is not a weak recommendation. It is an accurate one, and the decision-maker needs to know it before committing a quarter's budget.

## Before finishing

- Does every figure name its sheet and its months?
- Is the recommended option matched to the metric it actually moves?
- Has the second priority been recalculated rather than re-described?
- Is there a figure in the table that nothing in the recommendation uses? Say why it is there or remove it.
